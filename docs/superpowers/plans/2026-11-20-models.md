# Models Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Users declare models (domains → models → fields) as parsed JSON, and each of the four generated languages loads them, finds a model by `domain:model` name, and validates a whole payload, reporting every bad field with a JSON Pointer, a fixed code and its params, ready for translation and RFC 9457 responses.

**Architecture:** A JS reference (`dev/lib/models.mjs`) and shared cases (a new `models` section in `dev/langs/cases.json`) define the behaviour. Each language gets one hand-written file, `dev/codegen/models.{py,ts,go,rs}`, which its emitter appends after `engine.*` in the same single dist file. The models engine calls the existing typed scalars by exact name. The generator adds two things the engines need at runtime: each type's `params` list, and a `PARAM_RULES` table built from `$meta.params`.

**Tech Stack:** Node 22 (`node --test`, ajv), Python ≥ 3.10, TypeScript (Node type stripping), Go ≥ 1.21 (`encoding/json` values), Rust (`regex`, plus new `serde_json`).

**Spec:** `docs/superpowers/specs/2026-11-20-models-design.md`. Read it first; this plan argues from it.

## Global Constraints

- Every behaviour in the spec, unchanged. Where this plan pins a detail the spec left open, the plan wins (listed under "Calls this plan makes").
- One API shape in all four languages: `models(data)` → set; `set.get("domain:model")` → model or nothing (matching existing `get`: `None` / `undefined` / `(nil, false)` / `Option`); `model.validate(payload)`; `model.is_valid(payload)`; set's `all` (sorted full names).
- Names: Python `scalars.models`, `Models`, `Model`, `ModelError`, `ModelsError`, `Problem`. TS: `scalars.models`, exported classes `Models`, `Model`, `ModelError`, `ModelsError`, type `Problem`. Go: `Models(data any) (*ModelSet, error)`, `ModelSet`, `Model`, `ModelError`, `ModelsError`, `Problem`. Rust: `models(&Value) -> Result<Models, ModelsError>`, `Models`, `Model`, `ModelError`, `ModelsError`, `Problem`. Add every new public name to the language's `RESERVED_*` list.
- Error lists are a field named `problems` (Python/TS/Rust) / `Problems` (Go), each `{pointer, code, params, message}` as in the spec's Errors section, sorted (see Task 3). `pointer` is RFC 6901 (`~` → `~0`, `/` → `~1`, root `""`). `params` is always an object/map, empty when there are none.
- Python and TypeScript stay dependency-free. Go uses the standard library only. Rust adds `serde_json` (no `preserve_order`).
- Validate is O(input) worst case. Load is O(file). No recursion driven by the input. Load resolution is iterative (explicit stack), so long reference chains can't overflow a stack.
- Never edit `dist/` by hand. Run `npm run build` in `dev/`. Shell heredocs collapse `\\` on this machine, so write files containing patterns with a file editor.
- `dist/scalars.json` doesn't change shape; it only gains `$meta.errors` (Task 1).
- Commit after each task, with the session's attribution lines. Don't touch `docs/HANDOFF.md` (the owner's file) except in Task 9, and only if the owner says so.

## Calls this plan makes (the spec left them open)

1. **Templates, exact text, in `$meta.errors`** (Task 1). Every language renders `message` from them by replacing `{name}` with the param (lists joined with `, `, numbers in plain decimal):
   - Payload codes: `required` → `Required.`, `unknown_field` → `Not a field of this model.`, `not_object` → `Must be an object.`, `not_list` → `Must be a list.`, `too_long` → `At most {max} characters.`, `not_allowed` → `Must be one of: {values}.`, `too_many_digits` → `Too many digits for precision {precision}, scale {scale}.`. `invalid` has no template: its message is the type's `error` text.
   - Models-file codes: `bad_name` → `Names are lowercase letters, digits and underscores, starting with a letter.`, `unresolved` → `No type or model by this name.`, `alias` → `This is an alias; write "{canonical}".`, `unknown_setting` → `This type takes no such setting.`, `bad_setting` → `This setting's value is out of range or the wrong kind.`, `missing_setting` → `This type needs "{setting}".`, `cycle` → `This reference leads back to itself.`, `too_deep` → `Models nest more than {max} levels deep.`. `not_object` is shared.
   - Which code applies: `required` = missing or `null` where not nullable (also a `null` list entry when `items` isn't nullable). `not_object` = the root, a model-typed value, or (in the file) a domain, model or field object that isn't an object. A top-level `$`-key other than `$schema` is `bad_name`. A field that is neither a string nor an object is `bad_setting` at the field. An object without a string `type` is `missing_setting` with `setting: "type"`. `scale` without `precision` is `missing_setting` with `setting: "precision"`, at `/…/scale`. `array` without `items` and `enum` without `values` are `missing_setting` at the field. `items` on a non-array, and `precision` on a number kind, are `unknown_setting`. A bad, duplicate or non-string `values` entry is `bad_setting` at `/…/values/i`.
2. **Shared cases compare `pointer`, `code` and `params` exactly for both errors, and `message` exactly for payload errors.** Models-file messages come from the same templates, so they're compared too.
3. **Pointers into the models file:** `""` (root), `/billing`, `/billing/invoice`, `/billing/invoice/total`, `/billing/invoice/total/precision`, `/…/items` (repeatable: `/…/items/items`), `/…/values/2`. A bad top-level key is `/<key>`, escaped.
4. **`precision` / `scale` are refused at load on number-kind types** (only `sf_decimal` today). Float text differs by language (`1e21` vs `1e+21`), so one rule across four languages isn't possible. They're allowed on the text types `decimal`, `decimal128` and `uint64`, whose patterns only allow `-?[0-9]+(\.[0-9]+)?`.
5. **Model nesting deeper than 64 levels is refused at load,** at the field that makes it 65. This bounds validation's recursion (Python's default limit is 1000 frames) and doesn't depend on the input. Field-reference chains aren't nesting and are unlimited.
6. **`values` entries** must be strings, unique, and already clean: each must pass the type's `validate` unchanged. Otherwise it's `bad_setting` at `/…/values/i`.
7. A missing `scale` with a `precision` means `scale = 0` (Postgres `numeric(p)`). `scale` without `precision` is a load problem.
8. **Integers in Rust and Go:** a JSON number with an integral value (`3.0`) counts as an integer, as the reference and Python already do.
9. **`is_valid`** may stop at the first problem.
10. A cycle reports a problem at **every** field on it.

## Review Focus

1. **Unknown keys outside the BMP, and keys holding `/` or `~`**: JS sorts by UTF-16 units, Python and Rust by code point. Two unknown keys U+FFFF and U+1F600 (😀) must come back in code-point order (U+FFFF first) in all four. Sorting uses the decoded segments, never the escaped pointer text. An unknown key `a/b~c` is reported at `/a~1b~0c`. Test in Task 3 (cases `sort_astral`, `pointer_escape`).
2. **Keys like `__proto__` and `constructor`**: TS and the reference must look fields up with `Object.hasOwn` and build the output so that a payload key `__proto__` is reported as `unknown_field` at `/__proto__` (not merged into the prototype), and a model field named `constructor` works. Test in Task 3 (case `proto_keys`), run by every runner.
3. **`true` for an `int32` field and `3.0` for an `int32` field**: the boolean fails with int32's error text. `3.0` passes as `3`. Python's `bool` is an `int`, and Go/Rust JSON numbers are floats. Test in Task 3 (case `int_shapes`).
4. **A 5,000-long field-reference chain** (`f0` → `f1` → … → `string`) loads without stack overflow in all four. Test in Task 3 (hostile kind `ref_chain`).
5. **`null` where a model value belongs**: a non-nullable model field holding `null` gives `required`, not `not_object`. A root of `[]` or `"x"` gives one `not_object` at `""`. Test in Task 3 (case `null_vs_object`).

- [ ] **Step 4: Implement `validateModel`.** Recursion follows the resolved `Field` graph (at most 64 deep), never the input's own depth. Fields go in declared order. Unknown keys are checked with `Object.hasOwn` on the model's field map, never `in`. The output object is built with `Object.defineProperty` (or by assigning onto `Object.create(null)` and returning a plain copy), so `__proto__` can't change it. Length counts code points. `values` lookup uses a `Set` built at load. Problems carry `segments` (strings and integers) and are sorted by them, segment by segment: integers numerically; strings by code point (compare with `codePointAt`, not `<`); a shorter prefix first. The pointer is rendered from the segments (RFC 6901: each segment `~` → `~0` then `/` → `~1`, joined with a leading `/`; no segments → `""`). The digits rule runs on the cleaned text, in one pass:

```js
// Reject exactly what Postgres numeric(p, s) refuses. t = cleaned text matching -?[0-9]+(\.[0-9]+)?
function fitsNumeric(t, p, s) {
    if (t[0] === "-") t = t.slice(1);            // index offset in real code; no copies needed
    const dot = t.indexOf(".");
    const intLen = dot < 0 ? t.length : dot;
    const D = dot < 0 ? t : t.slice(0, dot) + t.slice(dot + 1);   // digits, point removed
    const k = intLen + s;                         // digits kept: R = round(value * 10^s) as an integer
    if (k < 0) return true;                       // rounds to 0
    let z = 0; while (z < D.length && D[z] === "0") z++;           // first nonzero digit
    const kept = Math.min(k, D.length);
    const nd = z < kept ? k - z : 0;              // digits of R before carry (padding zeros count)
    const carry = k < D.length && D[k] >= "5";
    let nines = true; for (let i = z; i < kept; i++) if (D[i] !== "9") { nines = false; break; }
    if (k > D.length) nines = false;              // padding zeros are not 9s
    return nd + (carry && nines ? 1 : 0) <= p;    // R < 10^p
}
```
  (Write it without the `slice` copies in the real code: index around the `-` and the point.)
